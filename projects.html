Field firmware update for IP intercom nodes

As a junior embedded software engineer, I extended a legacy WinForms configuration and maintenance tool for SIP/VoIP intercom nodes deployed in high-security sites. The tool discovers nodes over UDP, reads and writes their settings, and updates their firmware. Site visits are costly and access is restricted, so the client's own staff flash live devices over Ethernet. The update path therefore had to send the correct image to the correct hardware and report every node that failed.

I inherited a code base dating from 2017 or earlier and had no prior C# experience. I delivered firmware update, per-input change-of-state reporting and codec selection. I also corrected three existing faults and wrote the user manual.

Firmware update

  • I replaced the tool's built-in UDP download, which had been written only for the dsPIC33 nodes, with the command-line loader already used in production programming. Field updates and factory programming now share one proven method.
  • I added support for four device variants on two processor families. There are two node types, each with an older dsPIC33 hardware revision and a newer STM32F7 revision, and each variant has its own Intel HEX image.
  • I sorted the selected nodes into four lists using the hardware version and node type that each node reports in its discovery response, so the operator never has to identify hardware by hand.
  • For each node, I started one loader process and passed it the local IP address, target IP address, HEX file, processor family and device type as arguments. I waited for the process to exit and treated a non-zero exit code as a failure. The tool lists the failed nodes by IP address at the end of the run.
  • My first version, in July 2023, generated a single batch file covering every node. I replaced it in September 2023 with the per-node process model, because a batch run could not give me a result for each node.
  • I updated the nodes one at a time by unicast address, because some client sites had switches that did not support multicast.
  • I wrote a firmware selection form with one file picker per variant. Each dialog filters on that variant's file-name pattern, and the code rejects a name that does not match. This is a second layer in front of the firmware's own image validation. A confirmation dialog names the file before anything is sent.
  • I stored the loader path and the four firmware selections as .NET user settings, so they survive a restart.

Protocol extension

  • The proprietary protocol uses a fixed-layout UDP datagram. It carries two magic words, a sequence number, a return port, a packet count, a 16-bit command word and twenty 16-bit data words. The only specification was a spreadsheet seven years out of date, which described four inputs and had no codec field.
  • I compared that specification with the existing C# source to find which data words and bits were in use and which were free. I then placed the new settings in spare space in existing commands instead of adding new command codes.
  • For per-input reporting, the settings command carried one byte that had only ever held 0 or 1. I kept bit 0 as the global enable and used bits 1 to 6 as a mask for inputs 0 to 5, so the old value keeps its meaning. I packed the byte on write and decoded it in both code paths that parse the node's settings response.
  • I proposed codec selection after noticing that nodes in the field ran different codecs and that a mismatch degraded the audio. I used a data word in the audio settings packet that had always been sent as zero. The low byte holds the codec and the high byte holds the update flag, following the protocol's existing keep-or-update convention.
  • The codec value is the standard RTP payload type: 0 for PCMU (G.711 µ-law) and 9 for G.722. The tool also displays the value that the node reports back.
  • I agreed the bit and word positions with the engineer who maintained the node firmware before either of us changed any code. He made the matching firmware changes and updated the specification.

Faults found and corrected

  • I captured the tool's datagrams in Wireshark, compared them field by field with the specification, and found that the set-MAC-address command was sending the wrong sub-command. After correcting it, I changed a node's MAC address, power-cycled the node and confirmed that the new address had been retained.
  • The tool sent 0 for both trigger-high and trigger-low on two inputs, so an active-high trigger could not be configured. I corrected the encoding and added read-back of the function and trigger settings from the node.
  • The trigger time for one input was being read from another input's text box. I traced the fault from incorrect behaviour on a node back to the form code and corrected it.

Testing and documentation

  • I tested against real hardware on a bench test jig. I ran firmware updates on all four variants and on up to 10 nodes in a single run. After each update, I checked the audio quality, the stored configuration and the node's functions.
  • I wrote a seven-page user manual with 14 annotated screenshots for the client staff who run the updates. It covers loader and firmware selection, how to tell old hardware from new hardware for each device, and how to read the result dialog.

Limitations and what I would change

  • The update loop ran on the UI thread, so the main window was blocked during a run. I would move it to a background task with progress reporting and cancellation.
  • I read the loader's standard output to the end before reading standard error, which can deadlock if the child process fills the error pipe. I would read both streams asynchronously.
  • The tool captured the loader's output but did not show or log it, so the failure dialog gave only the IP address. I would log the output for each node and add a retry for failed nodes.
  • Validation was by file name only, so a renamed file would pass my check, and a node with an unrecognised hardware version fell into a default list. I would validate the image itself and reject unknown hardware explicitly.
  • With more C# experience, I would call the loader's library (DLL) directly instead of starting it as a separate process. That would give the tool direct access to progress and error information and would remove most of the issues above.

Ethernet PHY failure investigation, board repair and QA

After the software project, I moved to the hardware of the same product family: an IP intercom node built around an STM32F7 and a two-door access control board built around an STM32F407 and a KSZ8863 three-port Ethernet switch. Both boards are installed in high-security sites and connect to long runs of external supply, network, speaker, reader and lock wiring. I did component-level fault-finding and repair on production and field-return units, found the root cause of an Ethernet failure affecting more than 300 boards, repaired the production test jig, and later took on quality assurance sign-off.

Ethernet PHY failure investigation

  • More than 300 access control boards could not be discovered over UDP, both on the production line and in the field.
  • Affected boards still responded over Bluetooth. That told me the microcontroller, its firmware and its supply were working, so I confined the search to the Ethernet path.
  • Boards from earlier builds of the same design worked correctly, which gave me a known-good reference. I compared a failing board with a good board, circuit by circuit, in a fixed order.
  • I checked the 3.3 V digital and analogue rails and the 1.8 V rail at the device pins after the ferrite beads, the 25 MHz crystal and the clock outputs to the controller, the reset release and strap pin levels against the datasheet, and the transmit bias resistor and voltage.
  • On the line side, I checked continuity and resistance through the magnetics, termination networks and isolation capacitors, then ran a link and data-transfer test on both ports against a known-good partner.
  • The surrounding circuitry matched the schematic and the good board. The only difference was the switch IC itself, which ran hot whenever the board was connected to a network.
  • The devices on the failing boards carried different package markings from those on the good boards. They were counterfeit parts with a lower temperature rating than the specified industrial-grade KSZ8863MLLI, which the supplier admitted when it was raised.
  • I reported the finding to my supervisor, procurement and the workshop manager. The company changed supplier and the failures stopped.

Rework

  • I reworked about 50 boards myself. I removed the 48-pin fine-pitch device with hot air, cleaned the pads, fitted a genuine part and inspected the joints, then repeated the electrical checks and the link test on both ports.
  • I showed the workshop staff the rework method so that they could take over the remaining boards, and I checked their reworked boards afterwards.

Component-level fault-finding and repair

  • I studied the released schematics first, then followed the same sequence on every unit: inspect, form a hypothesis from the circuit, confirm it by measurement, repair, and test again. I did not replace parts by substitution.
  • On the supply input and 5 V buck regulator, I found high-resistance PTC fuses, TVS diodes that had failed short, damaged surge devices and out-of-tolerance parts in the timing and feedback networks. I confirmed each repair from the switching-node waveform on the oscilloscope and a step-load test of the rails.
  • On the speaker amplifier outputs, I found failed amplifier ICs, series resistors, coupling capacitors and open ferrite beads. I confirmed the repair by measuring output swing and DC offset. An open bead usually pointed to an earlier short on the site wiring, so I reported it for the installation to be checked.
  • On the line inputs, degraded coupling capacitors had shifted the bias point. I checked the DC bias against the calculated mid-rail level and spot-checked the frequency response at the filter corner frequencies of about 4.5 Hz and 7.2 kHz.
  • I traced intermittent link and power faults to dry or cracked solder joints and fractured pads, by monitoring the link or the rail while flexing the connector before and after rework.
  • On the access control board, I repaired the supply input and converters, the six opto-isolated lock-drive outputs, the two relay outputs, and the door-contact, exit-button and Wiegand reader inputs. I used the per-channel indicator LEDs and isolated grounds to separate logic-side faults from driver, MOSFET and load faults.
  • A design note on the power schematic records that a short on the 12 V reader output pulls down the 5 V and 3.3 V rails. A board that reset when a reader was connected therefore led me to the reader supply and boost stage, not the controller.
  • After each repair, I reprogrammed the unit, applied the default configuration, and confirmed that the firmware version and DIP switch settings matched the hardware build. Intercom nodes then went through a full call test covering call set-up, audio in both directions and clear-down.

Production test jig

  • I did the final functional test of each unit on an in-house test jig. It tested the Ethernet interface, the field inputs, the relay outputs and the lock-drive outputs.
  • The jig used a loopback arrangement. The unit's outputs switched relays inside the jig, and the relay contacts fed the unit's inputs, so each output was verified by reading the new state back on an input. A biometric reader in the jig exercised both Wiegand reader ports, A and B.
  • About two in five units were failing. The failures were intermittent, and units that had already passed sometimes failed on retest with no change to the unit. A defect in the product does not normally behave that way, so I treated the jig as the suspect and examined it before rejecting more units.
  • I checked the jig wiring for continuity with a multimeter and compared it with the existing wiring diagram. The wiring as built did not match the diagram, and none of it was labelled.
  • I then probed the jig's signals with an oscilloscope while a unit was under test. The interface board underneath the jig had an intermittent short that pulled a signal line low at random, so the signal was lost partway through a test and a good unit was reported as failed.
  • I also found loose connectors in the jig, which added further intermittent contact faults.
  • I rewired the jig to match the diagram and labelled every wire. I also replaced the pogo-pin contacts with plug-in connectors, which gave a positive, repeatable connection to the unit under test.
  • After the repair, false failures dropped to zero. Every failure the jig reported from then on was a real fault on the board being tested.

Quality assurance

  • My supervisor asked me to take on QA spot checks for these and other products. I had the authority to sign a unit out of the workshop or send it back for rework.

What I took from it

  • A matching part number does not prove that a part is genuine. Only the package markings, the temperature grade and the behaviour on the board showed the difference.
  • From this work, I identified measures to prevent a repeat: inspecting each newly sourced lot of the switch IC, recording date and lot codes at production for traceability, and adding a device read-back and a two-port link test to the production test.
