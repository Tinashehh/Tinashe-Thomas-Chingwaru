Field firmware update for IP intercom nodes

Made remote firmware updates possible for VoIP intercom nodes in secure facilities, where devices cannot be reached by hand and site staff update them over the live network. I extended the Windows maintenance tool with network firmware update, per-input event reporting and codec selection, designing each change against the node firmware and hardware on two processor families.

  • One tool now updates four device variants on two processor families, node by node, and reports exactly which nodes failed, so site staff know what still runs old firmware.
  • Proved the update cannot brick a node: cut power and pulled the Ethernet link mid-transfer on both hardware families, and every node fell back to its working image through the dual-bank flash fail-safe.
  • Studied the node hardware from its schematics before changing any software: a Cortex-M7 controller behind an on-board Ethernet switch, audio codec ICs on I2S and I2C, bridge-tied-load speaker amplifiers and six field inputs with configurable trigger level and debounce time.
  • Mapped the node firmware's command path end to end: LwIP UDP callbacks feeding a receive ring buffer, a command dispatcher, a retrying transmit queue and settings held as C structures in internal flash and read back after every write.
  • Traced both update paths through the node firmware, an in-application bank write with XOR checksum validation on the dsPIC33E and a boot-loader handover on the STM32F7 and used that analysis to replace the tool's built-in download with the proven production loader.
  • Added features to a fixed length UDP protocol without a single new command: the codec as an RTP payload type in a spare data word (G.711 at 8 kHz or G.722 at 16 kHz) and six input reporting flags in an existing byte, kept backward compatible with nodes already installed.
  • Root-caused three long-standing configuration bugs from packet captures and firmware source, including a MAC address command that used the read sub-command instead of the write sub-command, so nodes acknowledged and changed nothing. Verified every fix by power-cycling the node and reading the setting back from flash.
  • Diagnosed poor field audio as a codec and sample-rate mismatch and proposed and built the codec selection that fixed it.
  • Wrote the illustrated update manual for site staff and added per-variant file checks in front of the firmware's own hardware-version interlock.

Ethernet PHY failure investigation, board repair and QA

After the software project, I moved to the hardware of the same product family: an IP intercom node built around an STM32F7 and a two-door access control board built around an STM32F407 and a KSZ8863 three-port Ethernet switch. Both boards are installed in high-security sites and connect to long runs of external supply, network, speaker, reader and lock wiring. I did component-level fault-finding and repair on production and field-return units, found the root cause of an Ethernet failure affecting more than 300 boards, repaired the production test jig, and later took on quality assurance sign-off.

Ethernet PHY failure investigation

  • More than 300 access control boards could not be discovered over UDP, both on the production line and in the field.
  • Affected boards still responded over Bluetooth. That told me the microcontroller, its firmware and its supply were working, so I confined the search to the Ethernet path.
  • Boards from earlier builds of the same design worked correctly, which gave me a known-good reference. I compared a failing board with a good board, circuit by circuit, in a fixed order.
  • I checked the 3.3 V digital and analogue rails and the 1.8 V rail at the device pins after the ferrite beads, the 25 MHz crystal and the clock outputs to the controller, the reset release and strap pin levels against the datasheet, and the transmit bias resistor and voltage.
  • On the line side, I checked continuity and resistance through the magnetics, termination networks and isolation capacitors, then ran a link and data-transfer test on both ports against a known-good partner.
  • The surrounding circuitry matched the schematic and the good board. The only difference was the switch IC itself, which ran hot whenever the board was connected to a network.
  • The devices on the failing boards carried different package markings from those on the good boards. They were counterfeit parts with a lower temperature rating than the specified industrial-grade KSZ8863MLLI, which the supplier admitted when it was raised.
  • I reported the finding to my supervisor, procurement and the workshop manager. The company changed supplier and the failures stopped.

Rework

  • I reworked about 50 boards myself. I removed the 48-pin fine-pitch device with hot air, cleaned the pads, fitted a genuine part and inspected the joints, then repeated the electrical checks and the link test on both ports.
  • I showed the workshop staff the rework method so that they could take over the remaining boards, and I checked their reworked boards afterwards.

Component-level fault-finding and repair

  • I studied the released schematics first, then followed the same sequence on every unit: inspect, form a hypothesis from the circuit, confirm it by measurement, repair, and test again. I did not replace parts by substitution.
  • On the supply input and 5 V buck regulator, I found high-resistance PTC fuses, TVS diodes that had failed short, damaged surge devices and out-of-tolerance parts in the timing and feedback networks. I confirmed each repair from the switching-node waveform on the oscilloscope and a step-load test of the rails.
  • On the speaker amplifier outputs, I found failed amplifier ICs, series resistors, coupling capacitors and open ferrite beads. I confirmed the repair by measuring output swing and DC offset. An open bead usually pointed to an earlier short on the site wiring, so I reported it for the installation to be checked.
  • On the line inputs, degraded coupling capacitors had shifted the bias point. I checked the DC bias against the calculated mid-rail level and spot-checked the frequency response at the filter corner frequencies of about 4.5 Hz and 7.2 kHz.
  • I traced intermittent link and power faults to dry or cracked solder joints and fractured pads, by monitoring the link or the rail while flexing the connector before and after rework.
  • On the access control board, I repaired the supply input and converters, the six opto-isolated lock-drive outputs, the two relay outputs, and the door-contact, exit-button and Wiegand reader inputs. I used the per-channel indicator LEDs and isolated grounds to separate logic-side faults from driver, MOSFET and load faults.
  • A design note on the power schematic records that a short on the 12 V reader output pulls down the 5 V and 3.3 V rails. A board that reset when a reader was connected therefore led me to the reader supply and boost stage, not the controller.
  • After each repair, I reprogrammed the unit, applied the default configuration, and confirmed that the firmware version and DIP switch settings matched the hardware build. Intercom nodes then went through a full call test covering call set-up, audio in both directions and clear-down.

Production test jig

  • I did the final functional test of each unit on an in-house test jig. It tested the Ethernet interface, the field inputs, the relay outputs and the lock-drive outputs.
  • The jig used a loopback arrangement. The unit's outputs switched relays inside the jig, and the relay contacts fed the unit's inputs, so each output was verified by reading the new state back on an input. A biometric reader in the jig exercised both Wiegand reader ports, A and B.
  • About two in five units were failing. The failures were intermittent, and units that had already passed sometimes failed on retest with no change to the unit. A defect in the product does not normally behave that way, so I treated the jig as the suspect and examined it before rejecting more units.
  • I checked the jig wiring for continuity with a multimeter and compared it with the existing wiring diagram. The wiring as built did not match the diagram, and none of it was labelled.
  • I then probed the jig's signals with an oscilloscope while a unit was under test. The interface board underneath the jig had an intermittent short that pulled a signal line low at random, so the signal was lost partway through a test and a good unit was reported as failed.
  • I also found loose connectors in the jig, which added further intermittent contact faults.
  • I rewired the jig to match the diagram and labelled every wire. I also replaced the pogo-pin contacts with plug-in connectors, which gave a positive, repeatable connection to the unit under test.
  • After the repair, false failures dropped to zero. Every failure the jig reported from then on was a real fault on the board being tested.

Quality assurance

  • My supervisor asked me to take on QA spot checks for these and other products. I had the authority to sign a unit out of the workshop or send it back for rework.

What I took from it

  • A matching part number does not prove that a part is genuine. Only the package markings, the temperature grade and the behaviour on the board showed the difference.
  • From this work, I identified measures to prevent a repeat: inspecting each newly sourced lot of the switch IC, recording date and lot codes at production for traceability, and adding a device read-back and a two-port link test to the production test.

Door controller firmware: new pneumatic door type, PLC integration and field faults

I was the engineer responsible for the firmware of a two-door access controller used in high-security sites. It runs on an STM32F417 with FreeRTOS and LwIP, and communicates over Ethernet, DeviceNet, Wiegand and Bluetooth. One firmware image supports 17 door types, including sliding and swing doors, gates, turnstiles and pneumatic doors. The controller reads card readers, door sensors and lock-bar contacts, and drives valves, locks and relays. I inherited a code base dating from 2016, having already repaired and tested the same board at component level. Over nine releases, I designed a new door type, integrated it with the site PLC, and investigated and corrected faults reported from the field.

New door type: pneumatic passage door

  • A site upgrade needed a large pneumatic sliding door that releases its air pressure once it reaches the fully open or fully closed position. None of the existing door types did this.
  • I extended the existing pneumatic door control, which already handled the unlock, open and close valves and the travel timeouts and was proven on site, instead of writing a new control function.
  • The design needed two more valve outputs than the controller had spare. I reassigned the second door's outputs to the two pressure-release valves and accepted that a controller set to this type operates one door only. A hardware change would have delayed the site upgrade.
  • The sequence I implemented switches the unlock valve on, waits for the lock-bar contact to report unlocked, and then drives the open or close valve. Travel ends when the optical end-position sensor is reached or the travel timeout expires.
  • At the end of travel, the controller switches all the valves off, waits about 1 second for the lock bar to drop, and then pulses the pressure-release valves for 2 seconds.
  • A command to move to the position the door is already in is ignored, and a movement in progress is cancelled if the Ethernet link to the control room times out.
  • I added the new type to the controller firmware, the Bluetooth commissioning app and the PC configuration software, so that it could be selected and monitored from each.

PLC integration over DeviceNet

  • On this site, a PLC supervises the controllers over DeviceNet, alongside the Ethernet control-room system, and decides from each door's status bits whether the door is secure.
  • The site had reported problems finding the controllers with Rockwell RSLinx. I set up RSLinx on a virtual machine at the office and replicated the problem, which gave me a network connectivity test that every firmware build had to pass before release.
  • The PLC needed the lock status of a swing door from the lock sensor alone, while other sites needed the combined result of the locked and unlocked sensors. I added a stored setting that selects between the two, and corrected the DeviceNet code for both the polled and the change-of-state messages.
  • The PLC could not read the secure status of the new passage door, because the general sliding-door status logic was also running for the new type. I changed its condition to list exactly the door types it applies to.

Field faults investigated and corrected

  • Two weeks after the passage door went into service, its pressure-release valves stopped working after a while. The fault was in my own design. I had sequenced the release with three state flags inside a branch that only ran when no movement command was active. A short or cancelled movement could leave the flags in a combination from which the sequence never restarted.
  • I moved the release logic to the top of the control function, where it runs on every cycle, and replaced the three flags with two countdown timers. A timer always runs down to zero, so the sequence cannot be left in a state that it does not recover from.
  • The second card reader on turnstiles stopped working after some time. The change log showed the same symptom at another site in 2019, so the fault had been in the firmware for at least six years. It was intermittent and appeared only on site, so I rebuilt a two-reader turnstile setup at the office and ran repeated tests until I could trigger it.
  • The cause was a race between the two readers. The control code acts on a reader's flag only on its rising edge. When both readers set their flags in the same cycle, the code served reader A and cleared only reader A's flag, so reader B's flag stayed set and could never produce another edge. I now clear both flags when either reader is served, and I confirmed the fix on the same test setup.
  • Settings from the Bluetooth app and from the PC software arrive in different layouts but were parsed by one function, so some timeouts could not be set correctly. I split the parsing into one handler per source, with a shared routine that saves to flash.

Robustness and field maintainability

  • Doors behaved incorrectly when a delay was set to zero or when the settings area of flash held no valid data. I added start-up validation that rejects blank or zero values and applies known defaults for the network settings and the door timings. A controller with erased or corrupt settings now starts in a known state and stays reachable on the network.
  • A client needed the turnstile output held for 3 seconds to drive a magnetic lock, instead of a short pulse. I first made the time selectable with a DIP switch. The client then explained that opening installed units was impractical, so the next day I inverted the logic to make 3 seconds the default. Installed units then needed only a firmware update over the network and no site visit.
  • A client could not upgrade very old units to the current firmware. I established that units below a certain version must first be updated to an intermediate version, and I documented the procedure in the change log for the team and the client.
  • I extended the pneumatic cell door mode from one door to two doors per controller.
  • Every change had to preserve the existing safety behaviour: manual override monitoring, obstruction detection from door speed, travel timeouts and a cushion zone, and cancelling movement when communication is lost.

What I took from it

  • Timing and sequencing for valves and lock bars cannot be settled from the code alone. They have to be exercised on the real door over many cycles.
  • An intermittent fault has to be reproduced before it is fixed. Otherwise the fix is a guess.
  • How the client will maintain the product in the field is part of the requirement. I now ask how a setting will be changed on installed units before I choose how to implement it.
  • I would make the valve and release timings configurable settings, keep a permanent bench rig with two readers and a PLC connection, and run a regression checklist for every door type before each release.

Management and alarm software for networked electronic safes

I was the developer of two PC programs that serve more than 20 networked electronic safes installed at a client's retail sites. The safes open by PIN, card or face recognition, enforce time delays and door interlocks, and raise tamper, duress and forced-entry alarms. The first program is the operators' management tool for status, settings, users, door operation, firmware updates and event logs. The second is the alarm link, which polls the safes over UDP, converts their events to Contact ID messages in a receiver format and forwards them over TCP to the client's alarm monitoring software. I took over both programs from earlier developers, and all later versions are my work.

From a single-user tool to a server and client system

  • The inherited tool ran on one PC for one user and kept its device list in a local file. The client needed several control-room operators working on the same safes, an event history that outlives any one PC and control over who may change what.
  • I agreed the architecture with my supervisor and then built it. The server runs on a remote machine and the clients run in the control room, with no direct route between them, so I made a MySQL database the link between the two.
  • The server polls the safes, records their status, writes events to the log and publishes shared settings such as the safe list and firmware files. Each client synchronises its safe list with the database on start-up.
  • A client cannot ask the server directly whether it is running, so the server writes a heartbeat to a status table while it polls. Each client reads the newest entry and treats the server as down when the entry is stale, and shows this on a green, orange or red status bar. Operators therefore know when the picture on screen is out of date.
  • The server refuses to start if another instance is already running, so that two servers cannot poll the same safes.
  • I put all database operations on a thread-safe queue served by a worker thread, so that neither the user interface nor the UDP communication waits for the database. I added locks on the lists that the UDP layer shares between threads.
  • I implemented role-based access control with three roles: administrator, manager and user. Ordinary users can view and operate a safe, and only a manager can remove a safe or manage logins.

Features for operators

  • I built the safe view window that the client had asked for, from which operators see each safe and operate it remotely.
  • I added an alarm column on the main window that flags conditions such as a disabled safe, a disabled interlock or a clock out of sync, and a window that shows how many messages each safe is sending to the alarm link per minute.
  • I blocked other packets during a firmware update, and added migration of safe users when upgrading across a change in the firmware's memory layout.
  • I fixed list flicker and unwanted re-selection caused by automatic status packets, and added CSV import, time synchronisation and input length limits.
  • Older safe firmware ignored a settings packet of the wrong length. I padded the packet to the expected length in the software, which restored the function for safes already in the field without a firmware change.

Event log reports

  • The server records each safe's events in the database: the time, shop number, user number, message, door number and the safe's IP address. The client's manager needed to review this history after an incident, to see who opened which door, without having access to the database itself.
  • I added a report window to the client application. The operator chooses a date range and requests the events of one selected safe or of all safes.
  • The software runs a parameterised SQL query against the event table for that range, loads the result into a report template and exports it as a PDF. I used the open-source FastReport library for the template and the export, instead of writing a PDF generator myself.
  • Each report is saved with a timestamp in its file name, in a folder for that safe or a separate folder for all safes, so an earlier report is never overwritten. The single-safe button is disabled until a safe is selected, and the operator must confirm before a report is generated.
  • I chose PDF over a spreadsheet export because the report may be relied on after an incident and should not be easy to alter. A PDF is not tamper-proof, so the database remains the authoritative record, and a report can be generated again from it for comparison.

Guided production test page

  • I noticed that technicians were taking a long time to test each safe by hand from a paper sign-off sheet. Nobody had asked for a tool, so I proposed and built one into the software.
  • The page takes the technician through eleven stages in a fixed order.
  • At each stage, the page either drives the safe itself or prompts the technician, then waits for the safe to report the matching result and marks the stage OK or FAULTY. It checks for conditions that would spoil a result, such as a door that is already open and allows a retry.
  • I used a colleague's existing manual test procedure as the specification. The page saves a timestamped report for each safe, which replaces the hand-written sheet.
  • I timed myself testing one safe each way. The manual sheet took about 20 minutes and the test page took less than 5 minutes.

Alarm link to the monitoring software

  • The alarm link had been written for intercom nodes. I extended it to the safes, so that their Contact ID events are forwarded in the required format, and added a configuration file that maps each access card to a user in the monitoring software.
  • After release, safe events were not handled correctly. I traced this to the event qualifier, which the safe already sent in the required form while the program expected the unconverted form, so its case statement never matched. I corrected the handling.
  • A safe that stops communicating cannot report an alarm. I added connection monitoring that records each safe's last reply and sends a communication-trouble event when a safe goes offline and again when it returns. I set the timing from real network and power outages on site, so that brief outages do not raise false alarms that operators learn to ignore.
  • The safes are polled in slots, not all at once, to spread the network traffic.
  • The safes enforce operating hours and time delays, so I added automatic clock correction when a safe's time drifts by a minute or more.

Alarm flood protection

  • The control room was being flooded with the same message repeatedly. The cause was one safe with a loose connection on an input, which changed state continuously and every change was forwarded as a genuine event.
  • I added rate limiting for each combination of safe and event code. Once a safe repeats the same event beyond a threshold within a minute, further copies are blocked, while its other events and all events from other safes still go through.
  • I added a traffic window that shows each safe's status and its message count for the last minute, so that a misbehaving safe can be identified at once.

Testing and commissioning

  • I had no copy of the client's monitoring software, so I wrote my own TCP server to stand in for it and verified the exact messages and format the alarm link produced for each safe event.
  • I then tested on the live system in the client's control room with their security team, working through each alarm type together.
  • I built a diagnostics window that sends test and custom messages on demand. The security team used it to configure the alarm types on their side without anyone having to force a real alarm at a safe.
  • I ran each version of the management software through repeated tests against a safe test jig before release, and the decision to release was mine.
  • I wrote the client user manual, covering first-time setup, the safe view and its twelve groups of settings with their defaults, each alarm with its risk and remedy, and the event codes.

What I took from it

  • Software that reports to a monitoring station must be designed for a misbehaving device, not only for the normal case. Repeated messages carry no new information and hide real alarms.
  • A system must say when it is not working. Without the heartbeat, an operator could watch a screen that looked normal while the server was down.
  • Watching the users is as useful as reading the requirements. The test page came from noticing how long the technicians took.
  • I would move the rate-limit and offline thresholds and the fixed UTC+2 time offset out of the code and into settings, so that they can be tuned for a site without a new release.

Software · C# · WinForms · MySQL · Dec 2024–Sep 2025

Stock and ordering system, and production reporting tool

I wrote two internal Windows applications from scratch in C# for an electronics manufacturer. The first is a stock and ordering system of about 16,800 lines over a MySQL parts database, which replaced the Excel workbook the company had bought components from since 2018. The second is a production reporting tool of about 4,300 lines that reads the company's ERP database. I worked without day-to-day supervision: I gathered the requirements, designed and wrote the software, tested it with its main user and decided when it could replace the spreadsheet. Component ordering for the company now runs on this software.

The problem

  • The workbook held about 90 sheets, mostly one bill of materials (BOM) per product, and about 6,900 lines of macro code that read from and wrote to the parts database. It had become slow, and capturing a new BOM took about 7 minutes.
  • Most of its functions were restricted to one person, so nobody else could safely create parts, order batches or check the state of an order.
  • It counted all stock on the shelf as available, even when another open batch had already claimed it, and it ignored parts on order that had not yet been delivered.
  • A wrong order quantity has a direct cost. Too few parts stops production, and too many ties up money in stock. The replacement therefore had to give the same answers as the trusted spreadsheet before anyone could rely on it.

Requirements and design

  • There was no written specification. I sat with the procurement manager and had each step explained: capturing a BOM, building a batch from one or more BOMs, raising an order against a batch and booking in deliveries. I then read the workbook's formulas and macro code to confirm what each column calculated.
  • I built the application in C# with Windows Forms directly on the existing MySQL parts database, so that no data had to be migrated and the spreadsheet and the new software could run side by side on the same data.
  • The application has separate windows for parts, BOMs, batches, the batch manager, orders, deliveries and kits. A second database connection reads the ERP system for purchase orders, sales orders and finished-goods stock.
  • I defined four user roles: administrator, ordering, engineering and assembly manager. Each role is limited to the functions that person's work needs, following the principle of least privilege, so that a mistake or a misused login can only do limited damage.

Functions the spreadsheet did not have

  • The software warns at start-up about every part below its minimum stock level, and lists the orders not yet delivered. An order is marked delivered automatically from the quantities booked in.
  • A part can have more than one distributor, and the distributor's part number is filled in automatically on a new order.
  • An obsolete component can be replaced across every BOM that uses it in one operation, and the BOM options of a product are kept in step with each other.
  • The software exports the BOM for the contract assembly house and audits the BOM they return, reporting parts added, parts removed and reference designators that do not match.
  • Stock figures are synchronised with the ERP system.

Ordering calculations

  • For each part in a batch, the order quantity depends on the quantity needed, stock on hand, the minimum order quantity, the parts lost each time a reel is loaded on the pick-and-place machine, the quantity already ordered and the quantity already delivered.
  • I rebuilt each of the spreadsheet's calculations as a separate function, so that every result could be checked against the matching spreadsheet column.
  • The side-by-side comparison found three errors in my translation of the formulas: an order-of-operations error in the reel loss estimate, the wrong manual adjustment in one order quantity, and a missing adjustment in the outstanding delivery figure. I corrected all three before the software was used for real orders.
  • I replaced the raw stock figure with a moving stock figure: stock level, minus the quantity committed to other open batches, plus the quantity on other orders not yet delivered. My supervisor suggested the formula, and I confirmed that it matched the ERP system's definition of virtual stock before I implemented it.

SQL fault found and corrected

  • The procurement manager noticed a virtual stock figure that was wrong. I traced it to my own query, which joined each purchase order line to its delivery records and then summed the ordered quantity.
  • A line delivered in two or three part shipments has two or three delivery records, so the join counted its ordered quantity two or three times. The quantity on order was overstated, which made stock look healthier than it was and could hide a shortage.
  • I moved the ordered total into its own sub-query, so that the number of delivery records no longer affects it. The same fault existed in the reporting tool, and I corrected it there as well.

Verification and cutover

  • I treated the spreadsheet as the reference, because the company had ordered from it for years. I placed orders through both systems, using past orders as real test data, compared the results column by column and traced every difference to its cause.
  • Several functions needed new database columns while the database was in daily use. I copied the live database to a test database, made and tested each schema change there, and applied it to the live database only after it worked on the copy.
  • I kept the source in a Git repository on the company server, with a dated entry for each change describing what was changed and why.
  • I tested every function together with the procurement manager, and only then decided that the spreadsheet could be retired.
  • When the ERP system was later upgraded and its table and field names changed, I updated the queries in both applications to the new schema.

Production reporting tool

  • The tool reads the ERP database and shows the state of the company's orders in one place. Staff across the office use it to follow deadlines and deliveries.
  • It lists open order lines with quantity ordered, quantity delivered, creation date, deadline, priority, responsible person and workflow stage. It has separate views for purchase orders and sales orders, and filters by workflow stage, part name and part number.
  • Users can search by client and product for every order still to be delivered, change the responsible person and workflow stage, and edit the notes on each order line.
  • I added workshop tickets, which staff log, edit and close in the tool. The tickets are stored in the ERP system, so they are also visible there.
  • I produced a second build for an older version of the .NET Framework, so that the tool runs on the company's Windows 7 computers.

Outcome

  • The spreadsheet is retired, and component ordering runs on the software.
  • The procurement manager estimates that capturing a new BOM now takes about 2 minutes, against about 7 minutes in the spreadsheet.
  • Ordering is no longer limited to one person. Four kinds of user work on the same data, each with access suited to the role.

Limitations

  • Login names and access levels are fixed in the program. An administrator cannot add a user or change a role without a new build.
  • The assembly manager's restriction to one product family depends on the batch name containing that family's name, so a batch named differently would not appear for that user.
  • The software has no automated tests. Its correctness rests on the comparison with the spreadsheet and on testing with the users.
  • I did not write a user manual for either application.

What I took from it

  • Translating a formula is as error-prone as inventing one. Having a trusted reference to compare against is what caught my three errors.
  • A database join can silently multiply a total. I now check any summed figure against a hand count on a record that has more than one child record.
  • A process that exists only in one person's head has to be learned from that person before any code is written.
  • I started version control only after about 9,300 lines were written. On the next project, I would use it from the first day, write automated tests for the calculations, and manage users and roles in the database instead of in the code.
