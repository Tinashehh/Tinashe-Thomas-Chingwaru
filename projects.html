Field firmware update for IP intercom nodes

Extended a legacy Windows configuration tool for SIP/VoIP intercom nodes installed in high-security sites, where site visits are costly and restricted, so the client's own staff update live devices over the network. I added firmware update, per-input reporting and codec selection, fixed three existing faults and wrote the user manual.

Firmware update

  • Reused the production firmware loader instead of extending a separate UDP download, so field updates and factory programming share one proven method across four device variants on two processor families (STM32F7 and dsPIC33).
  • Classified each discovered node by its reported hardware version and node type, then updated nodes one at a time, because some client networks had switches without multicast support.
  • Replaced my first batch-file design with one process per node, so every node returns its own result and the tool lists exactly which nodes failed.
  • Added file-name checks per device variant and a confirmation step as a second safety layer in front of the firmware's own protection.
  • Tested on all four variants and on runs of up to 10 nodes, checking audio, settings and functions after each update.

Protocol extension

  • The only protocol documentation was seven years out of date, so I compared it with the existing code to map which of the 20 sixteen-bit data words per packet were in use and which were free.
  • Packed six per-input reporting flags into a byte that previously held only 0 or 1, keeping bit 0 as the overall enable so older values keep their meaning.
  • Proposed codec selection myself after noticing mismatched codecs were degrading audio in the field. Implemented G.711 µ-law / G.722 switching in an unused data word, using the standard RTP payload type numbers.
  • Agreed the packet layout with the firmware developer before either of us changed code.

Debugging and documentation

  • Captured the tool's packets with Wireshark, compared them with the protocol document and found the set-MAC-address command was sending the wrong sub-command. Verified the fix by power-cycling a node and confirming the address persisted.
  • Fixed input trigger polarity (high-level triggers could not be configured) and a copy-paste fault where one input read another input's timing value, and added read-back of those settings from the node.
  • Wrote a seven-page user manual with 14 annotated screenshots for the client staff who run the updates.

What I would do differently

  • Call the loader's library directly instead of launching it as a separate process, run updates off the UI thread, and log failure detail and retry failed nodes.
