How I work

  • Hypothesis-driven fault isolation. I work from the schematic, firmware and protocol to a testable hypothesis, then confirm it by measurement (oscilloscope, current and voltage measurement, packet capture) before any component or code is changed.
  • Reproduce under controlled conditions. Field faults are recreated on the bench with test fixtures, protocol test harnesses and instrumented builds, so the root cause can be isolated and the fix verified against the same stimulus.
  • System-level root-cause analysis. A symptom may originate in the hardware, the firmware, the host software, the network or the test equipment itself, so I isolate the fault domain before deciding on corrective action.
  • Fault injection, not just functional testing. I verify behaviour under power loss, link loss and malformed or repeated traffic, for example interrupting firmware updates to prove dual-bank fallback recovers the device.
  • Design for degraded operation. Watchdog supervision, acknowledged retransmission, rate limiting and fallback modes keep a system available and safe when a dependency fails.
  • Verification against a reference. Acceptance criteria are defined before release, and replacement systems run in parallel against a trusted reference until results match.
  • Risk-based prioritisation. Defects are triaged by operational impact. Anything that stops production or ordering is resolved first.
  • Configuration management. Version control, staged changes on a test copy before release, controlled database schema changes, traceable releases and user documentation.
